# P1 Windows lifecycle and capture follow-up

The Windows shutdown mitigation releases UI Automation providers on a normal Unity frame before final application teardown. The earlier #125 stack contains `UiaDisconnectAllProviders`, COM waiting and reentrant window messages after XR/Input teardown. This is a diagnostic lead, not a proven root cause. Microsoft requires provider cleanup before shutdown and disallows that COM operation from synchronous `SendMessage` handling: [API contract](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcoreapi/nf-uiautomationcoreapi-uiadisconnectallproviders).

`WorkspaceShutdown` defers a quit request out of the close-message handler, releases UIA providers while the window is alive, then lets Unity exit normally. It does not terminate the process, suppress crash reporting, change graphics/XR configuration or close Blender. The smoke path retains its success/failure exit code. The accepted interaction/startup/full-image baseline remains unchanged.
