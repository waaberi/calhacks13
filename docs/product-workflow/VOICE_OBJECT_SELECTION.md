# Controller pointing and explicit object selection

This repair is based on the exact tested main fbee0e1256ee56f77fb35eb70eb9ba65351710e5 build (final P2 plus voice, without P2.5).

Aim either controller's visible ray at an actual 3D model object. The voice status identifies the pointed object. Right-hand pointing takes priority when both rays hit different objects; the left hand is used when the right ray has no eligible object. There is no headset-gaze fallback. Mesh hits use the existing stabilized P2 aim and rendered mesh colliders, with nearer menu/screen/plane hits taking precedence.

Press and release that controller's front trigger to select the pointed object. Selection does not begin a grip, move an object or change native Blender selection/geometry. The **Select object** menu button shows the instruction for this action; **Clear selection** removes it. Hover is cyan; explicit selection is yellow and its name remains in the voice status. Selection stays latched when the ray moves away and after a voice command, until cleared, replaced, deleted or a document/session change.

Say a targeted command through the left menu push-to-talk button, for example **rotate it forty five degrees around x**. VoiceCore receives the selected UUID, so looking or pointing elsewhere does not replace an explicit selection. If a remembered command was only missing its target, selecting can complete that pending command, following the existing VoiceSession behavior. Cancel the pending command first if the intent is only to select.

Grips retain accepted workspace/individual-part movement, stick alignment and two-hand behavior. While a grip owns a target, a trigger keeps its existing alignment action and does not select. A trigger on a menu or screen cannot select a model behind it. Tracking/focus loss clears transient pointing and requires a fresh input edge; explicit identity survives ordinary focus loss, while pending voice commands/delete confirmations are cancelled. Disconnection, new document epoch, deletion or hidden/non-current object invalidate selection. Host authority and native command validation stay unchanged.

Software evidence: `VoiceSelectionChecks.Windows` runs actual production ray routing for both hands, local selection without drag/native mutation, latched VoiceSession target resolution, actual Select/Clear menu callbacks and GPU-rendered labels, screen/menu occlusion, existing grip/release, stationary-pointer dwell, focus, disconnection and document-epoch cleanup. It then runs the final P2, placement, scale, independent-plane, controller-pair, room/AppSpace replay, P1 drag/startup/freshness/visual gates and a Windows build. All passed. Capture/launcher unittest:30 passed. .NET10 CLI tests were not rerun because this PC has no .NET10 SDK; Unity's bundled SDK is8.0.318. The actual VoiceSession class is exercised in the Unity checks.

One initial test fixture compile failed by using a parameterless HostEvent constructor; fixed to the actual HostEvent(kind) API, and the failed log retained. SDK-generated settings were archived/inspected/restored; all34 Standalone XR feature flags match the base. No preview curvature, drag mapping, capture encoder, native add-on, schema, P2.5, other phase, PR or main changes.
